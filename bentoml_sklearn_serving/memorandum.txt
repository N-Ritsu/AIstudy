・開発目的
学習済みモデルを本番利用可能なAPIとして提供するMLOpsの一連の流れ（パッケージング・コンテナ化・サービング）を実践するため。

・技術選定理由
- BentoML：モデルのバージョン管理、API定義、依存関係込みのパッケージング、Dockerfileなしでのコンテナ化までを標準化できる。
- Scikit-learn（SVM + Iris）：サービングの仕組みを実証するための、シンプルで理解しやすい分類モデル／データセット。
- Docker / Docker Hub：生成したイメージをどこでも同じように動かせる形で配布・実行するため。
- requests：起動したAPIに対するクライアント検証用。

・苦戦した点
- 初めての本格的なモデルサービングで、学習コードとサービングコードをどう分離するかの設計に時間がかかった。
- BentoMLの概念（Bento、モデルストア、bentofile.yaml、service定義）を理解し、正しく連携させるのが難しかった。
- ローカルで動いても、コンテナ化後に依存関係やパスの問題が出ないようにする必要があった。

・苦戦点の解決法、工夫点
- 学習とサービングを明確に分離：train.py でモデルを学習してBentoMLのモデルストアに保存し、service.py では保存済みモデルを読み込んでAPIを定義する構成にした。
- bentofile.yaml でサービス・モデル・依存関係を宣言的に定義し、bentoml build → bentoml containerize の2コマンドで自己完結したイメージを生成。
- クラスベースの @bentoml.service と @bentoml.api で入出力の型を明示し、堅牢なAPIにした。
- 生成したイメージをDocker Hubにプッシュし、別環境から docker pull / docker run するだけで使えるようにした。

・得られた学び
- モデルを動かすだけでなく、再現可能で配布可能なサービスにすることがMLOpsの本質であること。
- Dockerfileを手書きしなくても、BentoMLのようなツールで本番向けイメージを標準化できること。
- Swagger UIが自動生成されることで、APIの検証と共有が非常に楽になること。

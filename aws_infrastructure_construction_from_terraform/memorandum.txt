・開発目的
学習したモデルをAPIとして提供し、それを安定稼働させるためのモダンなクラウドインフラ構築・運用スキルを身につけるため。

・技術選定理由
- Terraform：AWS上のECR・EC2・IAM・Security Groupをコードで定義・管理するIaC（コードによるAWSリソースの構築）の定番。
- Docker：アプリと依存関係をポータブルなイメージにパッケージング。
- GitHub Actions：pushをトリガーにイメージビルド～ECRプッシュ～Terraform applyまでを自動化。
- AWS（ECR / EC2 / IAM / SG）：コンテナ実行に必要な最小構成。
- FastAPI + Uvicorn：軽量なAPIサーバーとして採用。

・苦戦した点
デプロイ時に何度もエラーが発生し、特にTerraformの状態管理とAWSリソースの不整合が難しかった。

具体的にActionsで遭遇した主な問題：
- ECRリポジトリ（AWS版のDockerイメージ置き場）のイメージが残っている際に削除がうまく行かなかった。
- 前回の失敗で中途半端にリソースが残ったり、誤って手動操作してしまったことによるState（Terraformの、以前作ったAWSリソースの記憶）と現状の不一致から、terraform apply が失敗した。
- 1回の terraform destroy では依存関係や残存リソースを消しきれないケースがあった。
- AWS credentialsやIAMロール・ECRログインの設定ミスでビルド・デプロイが止まることがあった。

・苦戦点の解決法、工夫点
- ワークフローを"イメージビルド＆ECRプッシュ"と"Terraformによるインフラデプロイ"の2ジョブに分離し、needs（JobAの成功→JobBの実行） で順序を保証。
- デプロイ前に terraform refresh（Terraformが持っているStateと、現在のAWSの実際の状態を照合） → destroy（2回）→ state list でデバッグ情報を出し、強制的にクリーンな状態から plan / apply するフローを組んだ。
- ECRに force_delete = true を設定し、再作成時の削除エラーを回避。
- EC2の user_data で起動時に最新イメージをpullしてコンテナ起動する仕組みにし、アプリ更新を自動化。
- GitHub Secretsで認証情報を管理し、ソースに直書きしない構成にした。

・得られた学び
- 手動構築より、コード化されたパイプラインの方が再現性が高くミスが減ること。
- Terraformは強力だが、Stateと実リソースの整合性が崩れるとデバッグが難しくなること。
- CI/CDのエラーログを丁寧に読む習慣と、失敗を前提にしたクリーンアップ設計の重要性。
- インフラとアプリのデプロイを分離しつつ連携させる設計の考え方。

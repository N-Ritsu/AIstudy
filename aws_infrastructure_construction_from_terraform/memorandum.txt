・開発動機
働く上で、将来的にクラウドインフラの構築・運用スキルは必須になると考えていた。
特にアプリケーションエンジニアとしてAIや機械学習のモデルを実際にサービスとして提供しようとすると、コードを書くだけでなく、それを安定して動かすためのインフラ側の知識が必要になってくる。
しかし学生のうちにクラウドインフラを本格的に構築する機会はなかなかないため、どんなものかを実際に自分で動かして体験することで、実践的な知識が身につくと考え、このプロジェクトを開発した。
プログラムが書ける・AIの知識があるにとどまらず、クラウドインフラの構築からCI/CDによるデプロイ自動化まで、実践的な体験も積んでおきたかった。


・開発目的
学習したモデルをAPIとして提供し、それを安定稼働させるためのモダンなクラウドインフラ構築・運用スキルを身につけるため。
具体的に一番学びたかったのは以下の２点
- Infrastructure as Code（IaC）でインフラをコードとして管理すること
- CI/CDでデプロイを自動化する一連の流れを、実際に手を動かして体感すること


・技術選定理由（総じて、基本的に最もメジャーなものを選択している）
- Terraform：AWS上のECR・EC2・IAM・Security Groupをコードで定義・管理するIaC（コードによるAWSリソースの構築）の定番。
  [その他比較]
  - AWS CloudFormation：本プロジェクトではIaCの定番であるTerraformを使ってみたかったため選択しなかった。AWS公式で連携が強いが、AWS専用である。
  - AWS CDK：TypeScriptやPythonで書ける点が魅力だが、抽象度が高く、基盤となるCloudFormationの理解が必要になる。本プロジェクトの目的に対し過剰な学習コストだと判断した。
- Docker：アプリと依存関係をポータブルなイメージにパッケージング。
- GitHub Actions：pushをトリガーにイメージビルド～ECRプッシュ～Terraform applyまでを自動化。
  [その他比較]
  - Jenkins：高機能で自由度が高いが、サーバー管理が必要で、本プロジェクトの目的に対し学習・運用コストが高いと判断。
  - CircleCI / GitLab CI / AWS CodePipeline：GitHubリポジトリを使っている以上、GitHub Actionsの方が設定がシンプルで統合・管理しやすい。
- AWS（ECR / EC2 / IAM / SG）：サービスが豊富で信頼性が高く、Terraformとの連携も成熟しているため。コンテナ実行に必要な最小構成。
- FastAPI + Uvicorn：軽量なAPIサーバーとして採用。型ヒントを活用した開発ができ、自動ドキュメント生成機能も持つ。非同期処理に強く、コンテナ環境で動かしやすい。
  [その他比較]
  - Flask：シンプルで学習コストが低い。今考えると、この規模のプログラムであればFlaskで十分であった。
  - Django：フルスタックで高機能だが、API専用としては重く、学習コストが高い。このプロジェクトの目的には過剰だった。
- python:3.10-slim：通常の python イメージより不要なパッケージが少なく、イメージサイズを抑えられる。本プログラムならslimで十分と判断。
- t3.microインスタンスタイプ：無料枠の範囲内に収めるために小さなインスタンスタイプを使用。


・仕様、データフロー
このシステムは大きくインフラ構築フェーズとアプリケーションのデプロイフェーズに分かれている。
- インフラ構築フェーズ（最初の１回だけ実行想定。本プロジェクトではState不整合対策のため実質毎回実行に変更。）
  - terraform applyを実行
    - Terraformがmain.tfの定義に従い、以下のリソースを順番に作成
      - ECRリポジトリ
      - IAM Role
      - Security Group
      - EC2インスタンス
  - EC2インスタンスが起動すると、user_data に指定されたスクリプトが自動実行される。
    - パッケージのアップデート（yum update -y）
    - Dockerのインストールと起動
    - ECRへのログイン
    - 最新のDockerイメージ（:latest）のpull
    - コンテナの起動
- アプリケーションのデプロイフェーズ
  - 開発者がmainブランチにコードをpushする
  - GitHub Actionsがワークフローを開始する
  - Dockerイメージをビルドする
  - ビルドしたイメージに :latest タグを付けてECRにpushする
  - Terraformでインフラをデプロイする


・仕様理由
- 起動時に最新イメージをpullしてコンテナを起動する
  - インフラとアプリケーションのデプロイを分離するため（Terraformでインフラを構築した時点では、まだアプリケーションのイメージがECRに存在しないor古い可能性がある）
  - シンプルさを優先した（ECSのローリングアップデートやCodeDeployなど、学習用のプロジェクトとして複雑な仕組みを避けた）
  - 自動化の一貫性を保つため（GitHub ActionsでECRに :latest をpushしておけば、EC2を再起動・再作成するだけで最新のアプリケーションが反映される）
  [注意点]
  この設計だと、イメージを更新しただけでは既存のEC2上のコンテナは自動で更新されない。最新を反映するにはインスタンスの再起動や再作成が必要になる。
  本番運用では、ECSのサービス更新や、起動後に定期的にpullし直す仕組みなどを検討する必要がある。
- インフラ構築フェーズとアプリケーションのデプロイフェーズの分離
  - 役割と変更頻度が異なるため。インフラは一度作れば頻繁に変えないが、アプリケーションはコード修正のたびに頻繁に更新される
  - 責務を明確に分離でき、影響範囲を狭めることができる。
  [注意点]
  - 本プロジェクトでは、Stateの不整合対策として、GitHub Actions内で terraform destroy → apply を毎回実行する形になっている。そのためアプリ更新のたびにインフラも再作成されており、分離のメリットが十全に活かされていない。
  - 本プロジェクトでは上記の仕組みとなったが、作りなおすとしたらインフラを毎回作りなおす必要の無いように改善すべき。
- ECRのイメージタグを:latestにした
  - 学習用のプロジェクトとして、常に最新をとるというシンプルな構造にするため。
  [注意点]
  上書きされるため、過去の履歴をさかのぼれない。本番ではバージョン管理できるタグ運用をすべき。
- ECRに force_delete = true を設定した
  - 通常、ECRリポジトリの中にイメージが残っていると、Terraformでリポジトリを削除しようとしてもエラーになる。
  - 今回は、上記理由からエラーになることが多かったり、State不整合対策として毎回ほぼゼロから作り直す運用を行っていたため、スムーズな削除のために採用した。
  [注意点]
  - 誤って destroy を実行したときに、中のイメージごと消えてしまうリスクがあるため、本番環境では非推奨である。
  - 他の環境からも参照されているリポジトリでは、意図しないデータ損失につながる。
- templatefile関数を使っている理由
  - user_data.shに、Terraformが作成したECRリポジトリのURLを埋め込むために使用。
    - user_data.sh の中でどのECRリポジトリからイメージをpullするかを指定する必要がある。
    - しかし、ECRリポジトリのURLは terraform apply を実行するまで確定しない。
    - そのため、URLべた書きはできず、参照して動的に取得する必要がある。
    - main.tf内、EC2インスタンス定義においてTerraformのtemplatefile関数を用いて取得、それをuser_data.shに渡している。
- FargateではなくEC2を用いた
  - Fargateはサーバーを意識しなくて済むが、学習用のため敢えてEC2を用いた。
- 依存関係のインストール順を最適化
  - 先に requirements.txt だけをコピーして pip install → アプリケーションコード（app/）をコピー
  - コードだけを変更したときは、ライブラリの再インストールが走らず、ビルドが速くなる。
- --no-cache-dir オプション
  - pipのキャッシュを残さないことで、イメージサイズを小さくしている


・プログラムの流れ
１．開発者がローカルで terraform init → terraform apply を実行
２．main.tf が読み込まれ、リソースが順番に作成される
３．EC2インスタンス作成時に、user_data として user_data.sh が埋め込まれる
  - このとき templatefile 関数で、ECRのリポジトリURLが user_data.sh に動的に渡される
４．EC2が起動すると、user_data.sh が自動実行される
５．aws_infrastructure_construction_from_terraform/ 配下のコードをmainブランチにpush
６．ci_cd_pipeline_for_terraform.yml がトリガーされる
  １．ジョブ1：build-and-push-image
    １．リポジトリをcheckout
    ２．AWS認証情報を設定（GitHub Secretsから）
    ３．ECRにログイン
    ４．Dockerfile を使ってイメージをビルド
      - app/requirements.txt をインストール
      - app/main.py などをコピー
      - uvicorn app.main:app で起動する設定
    ５．ビルドしたイメージを fastapi-app-repo:latest としてECRにpush
  ２．ジョブ2：deploy-infrastructure（needs: build-and-push-image で、ジョブ1が成功した後にだけ実行される）
    １．リポジトリをcheckout
    ２．AWS認証情報を設定
    ３．Terraformをセットアップ
    ４．terraform init
    ５．強制クリーンアップ
      - terraform refresh
      - terraform destroy を2回
      - terraform state list で確認
    ６．terraform plan
    ７．terraform apply
      - 新しいEC2が立ち上がり、再び user_data.sh が実行される
      - 最新の :latest イメージをpullしてコンテナ起動


・苦戦した点
デプロイ時に何度もエラーが発生し、特にTerraformの状態管理とAWSリソースの不整合が難しかった。
具体的にActionsで遭遇した主な問題：
- terraform apply が何度も失敗した。
  [原因]
  - デプロイの途中でエラーになり、ECRやEC2が中途半端に残った
  - 手動でコンソールから触ってしまったことで、Stateが実態とズレた
  - terraform destroy を1回実行しても、依存関係や残存リソースを消しきれず、次の apply で衝突した
  - ECRにイメージが残っている状態でリポジトリを削除しようとして失敗した
- AWS credentialsやIAMロール・ECRログインの設定ミスでビルド・デプロイが止まることがあった。


・苦戦点の解決法、工夫点
- ワークフローを"イメージビルド＆ECRプッシュ"と"Terraformによるインフラデプロイ"の2ジョブに分離し、needs（JobAの成功→JobBの実行） で順序を保証。
- デプロイ前に terraform refresh（Terraformが持っているStateと、現在のAWSの実際の状態を照合） → destroy（2回）→ state list でデバッグ情報を出し、強制的にクリーンな状態から plan / apply するフローを組んだ。
- ECRに force_delete = true を設定し、再作成時の削除エラーを回避。
- EC2の user_data で起動時に最新イメージをpullしてコンテナ起動する仕組みにし、アプリ更新を自動化。
- GitHub Secretsで認証情報を管理し、ソースに直書きしない構成にした。


・得られた学び
- 手動構築より、コード化されたパイプラインの方が再現性が高くミスが減ること。
- Terraformは強力だが、Stateと実リソースの整合性が崩れるとデバッグが難しくなること。
- CI/CDのエラーログを丁寧に読む習慣と、失敗を前提にしたクリーンアップ設計の重要性。
- インフラとアプリのデプロイを分離しつつ連携させる設計の考え方。


・技術メモ
- Terraformは、.tfファイルに書かれたコードと現在の実態を比較し、差分を適用する
  - Stateファイル(通常はterraform.tfstate)は、自分が管理しているリソースの現在の状態を記録している
- terraform apply が失敗する典型的な原因一覧
  - Stateと実リソースの不整合 ← 今回の原因
    途中で失敗したり、手動でAWSコンソールを触ったりすると、State上の情報と実際のAWSの状態が食い違う。
  - 依存関係の問題
    リソース同士に依存関係がある場合、削除や作成の順番が正しくないと失敗する。
  - 権限不足
    - 実行しているIAMユーザーやRoleに、必要な操作権限が足りない。
  - 既に同名のリソースが存在する
    前回の残骸が残っていると、同じ名前で作成しようとしてエラーになる。
  - 認証情報の誤り
    AWSのアクセスキーやリージョン設定が間違っている。
- ビルド: アプリケーションをDockerイメージに変換する。
- terraform applyを実行するには、その前にDockerイメージをECRにプッシュしておく必要がある。
- Terraformコマンド一覧
  - terraform state list: State上で管理されているリソース一覧を見る。
  - terraform refresh: 可能な範囲でStateを実際の状態に合わせる。
  - terraform destroy: 残っているリソースを消す。1回で消しきれないこともある。
  - terraform plan: 差分を確認


・残る弱点、実務で使用するなら
- force_delete = falseにする
  - 誤って destroy を実行したときに、中のイメージごと消えてしまわないようにするため。
  - 他の環境からも参照されているリポジトリを消してしまうことで、意図しないデータ損失につながらないようにするため。
- 毎回terraform destroyをせずに、１度構築したインフラを再利用するようにする
- Stateをローカルではなくリモートに置く
  - チームで使う場合、全員が同じStateを参照しないと、お互いの変更を認識できず、意図しない削除や重複作成が起きてエラーにつながるため。
- GitHub Secretsにアクセスキーを保存しているが、長期キーは漏洩時のリスクが高いため、一時認証にすべき。
- EC2のIAMロールは最小権限だが、CI/CD用のアクセスキーに紐づけられている権限について具体的に定義しておらず、権限過多になっている可能性がある。最小権限を明示すべき。
- ヘルスチェック用のエンドポイントを用意していない。本番では用意すべき。
- 80番ポート(HTTP)、22番ポート(SSH)を公開しているためセキュリティが危険
  - Session ManagerでSSHポート自体を開けない、 ALBを前に置き443番(HTTPS)で受け付ける
- EC2一台構成のため、EC2インスタンスが落ちるとサービスも停止する。
  - Auto Scaling Groupを用いるか、Fargate に移行すべき。

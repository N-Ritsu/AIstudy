・開発動機
MLOps：機械学習モデルを作って終わりにするのではなく、本番環境で安定的に動かし続けるための一連の仕組み・実践のこと。
大学の学習用途では、作って終わりになりがちである。現場での運用を考え、継続的に動かし続ける仕組みを学びたいと思った。


・開発目的
安定運用してビジネス価値につなげるMLOpsについて理解するため。
機械学習モデルの 学習 → 評価 → デプロイ判断 までをAirflowで自動化したMLパイプラインを構築する。


・技術選定理由（総じて、基本的に最もメジャーなものを選択している）
- Apache Airflow：DAGでタスクの順序・スケジュール・監視・再実行を管理。バージョン管理しやすく、Web UIで直感的に実行状況・ログ・再実行を確認できる。
  [その他比較]
  - Prefect：Pythonネイティブで書きやすい。しかし本番運用事例やエコシステムはAirflowの方が圧倒的に多いため、学習のためAirflowを採用。
  - Kubeflow：Kubernetes上で動く本格的なMLOps基盤。学習コストが高く、本プロジェクトの規模には過剰であると判断。
  - 単純なcron + シェルスクリプト：簡単だが、依存関係管理・失敗時の再実行・ログ監視が弱く、運用に向かないと判断。
- Docker + Docker Compose：依存関係込みの再現可能な実行環境。安定運用の前提である再現性を確保するため。
  [その他比較]
  - ローカルに直接インストール：環境差異が起きやすく、再現性が低い。
  - Kubernetes：本番向きだが、学習用プロジェクトとしては過剰だと判断。
  - conda / venvのみ：Airflow本体や関連サービスの起動管理まではできない。
- pandas / numpy：CSVの読み込み、データフレーム操作、数値計算。
- scikit-learn（RandomForest）：分類のベースモデル。前処理〜評価まで統一的に扱える。高い予測精度とある程度の解釈性を両立でき、過学習しにくい。
  [その他比較]
  - Logistic Regression：シンプルで解釈しやすいが、非線形な関係を捉えにくく、今回のデータでは性能が劣る可能性が高い。
  - 決定木（単体）：過学習しやすく、RandomForestより不安定。
  - ニューラルネットワーク（PyTorch / TensorFlow）：過剰で、データ量も少ないため不適切と判断。
- BashOperator（Airflow）：Airflow上でシェルコマンドを実行するための部品。DAGの定義と実際の処理ロジックを明確に分離できる。ローカル実行用の run_local_pipeline.sh と同じコマンドで動かせるため、動作確認がしやすい。
  [その他比較]
  - PythonOperator：Python関数を実行できる。タスクを完全に独立したスクリプトとして扱いにくい。
- joblib + JSON：学習済みモデルと評価結果を成果物としてタスク間で受け渡し。
  [その他比較]
  - AirflowのXCom：小規模データ向き。数MBに達するモデルファイルには不向きで、永続性も低いため除外。メタデータベースが肥大化し、Airflow自体の動作に悪影響が出る可能性も考慮。
  - pickle：joblibの方がNumPy配列を含むscikit-learnモデルの保存に最適化されているためjoblibを優先。
- 評価KPIは悪性クラスのF1（見逃しコストが高いタスクを意識）。
- 乳がん診断データの使用：分類問題としてシンプルで再現性が高く、scikit-learnの標準データセットとして扱いやすいため。


・仕様、データフロー
このシステムは大きく環境構築フェーズとパイプライン実行フェーズに分かれている。
- 環境構築フェーズ（初回のみ）
  - Docker ComposeでAirflow一式を起動
  - カスタムDockerfileでscikit-learnなどの必要ライブラリを入れた実行環境を構築
  - DAGファイル（breast_cancer_dag.py）とタスクスクリプト群をAirflowのdagsディレクトリに配置
- パイプライン実行フェーズ（手動トリガー or スケジュール）
  - AirflowがDAGを読み込み、以下のタスクを順番に実行する
    - データ検証（入力CSVが存在するか・必要カラムが含まれているか・データが空じゃないか）
    - データ分割・前処理（train/test分割 + StandardScaler）
    - モデル学習（RandomForestClassifier）
    - モデル評価（classification_reportをJSONで保存）
    - デプロイ判断（悪性クラスのF1スコアが閾値0.90以上なら本番用モデルとしてコピー）
  - 各タスクは独立したPythonスクリプトとして実装され、成果物（中間ファイル）をディスク上で受け渡す
  - 実行状況・ログはAirflow Web UIで一元監視できる


・仕様理由
- 悪性クラスのF1スコアが0.90以上の場合のみ本番用モデルとしてコピーする
  - 医療ドメインでは偽陰性（悪性を見逃す）の重要度が非常に高いため、悪性クラスのF1スコアをKPIとした。
    - もしも全体AccuracyをKPIとすると、陽性より圧倒的に多い陰性にばかりフォーカスして、精度に関わらずほぼ全員を陰性としてしまう可能性がある。
  - 一定の品質を満たしたモデルだけを出すことで、運用リスクを下げ、ビジネス価値（信頼性）を担保するため。
- 性能評価によるデプロイ判断ロジック
  - 継続的な運用を前提とした際、なるべく人間の手間が発生しないよう、評価結果を自動で判断してデプロイするか決めるようにした。
- タスクを独立させ、成果物（joblib / JSON）でつなぐ設計
  - 失敗時にどこで止まったかを明確にし、該当タスクだけ再実行しやすくするため。
  - 運用時の障害切り分けと復旧を容易にすることを意識した。
  - 悪性クラスのF1スコアだけを抽出して閾値判定する際に、キーで値を取り出せるJSONが最も都合がいい。
- Airflow UIによる実行状況・ログの一元監視
  - 各タスクの成功/失敗と詳細ログをWeb UIで確認できる。運用負荷を減らすため採用。
- スケジュール実行（@daily）と手動トリガーの両方に対応
  - 定期的な自動実行で継続的な運用を可能にしつつ、開発・検証時には柔軟に動かせるようにするため。
- DAG定義と各タスクスクリプトを分離
  - パイプラインの流れと、各処理の中身を明確に分離し、疎結合な設計にするため。
  - タスク単位で開発・デバッグ・再実行がしやすい。
- train_test_splitによる学習用と評価用データの分離
  - 過学習を防ぎ、汎化性能を正しく測るため。
    - random_state を固定して再現性を確保
    - 比率は test_size=0.2
- StandardScalerを入れた理由
  - RandomForestは決定木ベースなので、特徴量のスケールの影響をほとんど受けない
    - 本プロジェクトだけならば、必要なかった。無心に特徴量のスケールをとりあえず行うのではなく、モデルに合わせてスケールするかどうかを決めるべきであると学んだ。
  - メリットとしては、線形モデルや距離ベースのモデルに差し替えても対応できる拡張性を得られることが挙げられる。
- ローカル実行用のシェルスクリプト（run_local_pipeline.sh）を用意した理由
  - Airflowを起動せずに、パイプライン全体のロジックを素早く検証するため
    - Airflowの起動・DAG反映・UI操作には時間がかかる。コード修正のたびにそれを繰り返すのは非効率であると考えた。
  - 各タスクを個別に実行して動作を確認できる。
- 毎日実行スケジュール(@daily)
  - 学習用の設定。実際の運用では、データの更新頻度やビジネス上の要求で決めるべき。


・プログラムの流れ
- docker compose up -d --build でAirflow環境を起動する。
- Airflowがdags配下のairflow_dag/breast_cancer_dag.pyを読み込む。
  - 以下の6つのタスクを、依存関係でつながれた順番に実行。それぞれのタスクはsettings.pyを参照する。
  - breast_cancer.csvを検証（setup_directories_and_data）
  - train.csv / test.csvを作成（validate_data）
  - model.joblibを作成（split_and_preprocess_data）
  - evaluation.jsonを作成（train_model）
  - evaluation.jsonから悪性クラスのF1スコアについて閾値判定（evaluate_model）
  - production_model.joblibを作成（deploy_model）


・主な設定値・結果
- パス・ハイパーパラメータ・閾値はsettings.pyにて一元管理している。
- データ：乳がん診断データ569件。学習用80%・テスト用20%（random_state=42）に分割し、テスト用は114件（悪性42件・良性72件）。
- モデル：RandomForest（n_estimators=100、max_depth=10）。
- デプロイ判断：悪性クラスのF1が0.90以上のときだけ本番用モデルとしてコピー。
- 評価結果（テストデータ）：悪性クラスのF1は0.9398（適合率0.9512、再現率0.9286）で閾値を超えたためデプロイ。全体の正解率は0.9561。


・苦戦した点
- 初めてのAirflowで、DAG定義・タスク分割・成果物の受け渡しをどう設計するかに時間がかかった。
- 環境構築や実行時エラーを、ログを追いながら切り分けること。
- 学習したら必ずデプロイ、ではなく、性能閾値でデプロイ可否を分ける判断ロジックの実装。
- Airflow環境でタスクを実行した際に、 ModuleNotFoundError: No module named 'pipeline_tasks'とエラーが出た。
  - Airflowのコンテナ内では、カレントディレクトリがプロジェクトルートではなかったため、ローカルでは普通に動くのに、Airflow上だと失敗する


・苦戦点の解決法、工夫点
- 処理を独立タスクに分割（データ検証 → 分割・前処理 → 学習 → 評価 → デプロイ判断）。
- DAGで依存関係とスケジュールを定義し、Airflow UIで成功／失敗とログを監視。
- 評価で悪性クラスのF1が閾値を超えたときだけ、本番用モデルとしてコピーするゲートを入れた。
- Docker ComposeでAirflow一式を起動し、再現性の高い実行環境にした。
- ローカルでも同じ順序で回せるシェルも用意し、開発時の確認をしやすくした。
- settings.pyにてパス・ハイパーパラメータ・閾値を一元管理。
- ディレクトリ内のpipeline_tasksを見つけられずエラーがでていたので、PYTHONPATHにプロジェクトルートを設定


・得られた学び
- MLOpsでは、モデル精度だけでなく、いつ・何を・どの条件で本番に出すかの自動化が重要であること。
- Airflowは実行の自動化に加え、エラー箇所とログを追いやすい点が運用で効くこと。
- タスクを小さく分ける疎結合を徹底すると、開発・テスト・再実行がしやすくなること。
- 単純な精度をKPIとするのではなく、業務視点で最も重要な指標をKPIに選ぶ考え方。
- 環境差異を無くすことの重要性


・技術メモ
- Airflow：機械学習やデータ処理の一連の作業を、DAGによって決められた順番で自動的に実行・監視・管理するためのオーケストレーションツール。
- DAG：Airflowにおける、どのタスクをどの順番で実行するかを矢印で表したもの。
- KPI：重要業績評価指標。プロジェクトやモデルが成功しているかどうかを測るための、一番大事な指標であり、本プロジェクトでは悪性クラスのF1スコア。
- モジュールを探す際の流れ
  １．今いるカレントディレクトリ内を探す
  ２．PYTHONPATH に登録されているフォルダ内を探す ← ここにプロジェクトルートを設定すれば、ディレクトリ内のどこにあっても見つけてくれる。
  ３．Pythonが標準で持っているライブラリの場所から探す
  ４．インストール済みのパッケージ内から探す


・残る弱点、実務で使用するなら
- 本プロジェクトでは、モデルのハイパーパラメータチューニングや実験管理は行わなかった。unsupervised_anomaly_detection_tracker_with_mlflowにてOptunaを用いた自動ハイパーパラメータチューニングと、MLflowでの実験管理を実装した経験があるため、実装の際はこのプロジェクトを参照する。
  [理由]
  - MLパイプラインの自動化と品質ゲートの実装を目的としていたため。
  - デフォルトのハイパーパラメータで十分なF1スコア(0.94)が出ていた。
- RandomForest以外のモデルで比較検討しなかった。classification_model_comparisonやregression_model_comparisonで複数モデルの比較を行っていたため、これらでの結果をもとにRandomForestに絞って実装した。
- 悪性クラスのF1スコア閾値を0.90と設定。本番は業務内容に応じて閾値を決めるべき。
- ファイルで成果物を受け渡しているため、複数人での作業ではファイルの共有・競合・パスの変更時に対応できない。ローカルファイルではなく、S3などの外部ストレージを検討すべき。
- リトライ戦略を入れていない。一時的な障害（ネットワーク、一時的なリソース不足）を想定し各タスクにretries=2〜3、retry_delay=timedelta(minutes=5)程度を設定するのが一般的。失敗時にメール通知を入れるのも案。
- データドリフトやモデル劣化の監視を行っていない。入れる場合、evidently_churn_monitorにて実装経験があるため、それを参照する。
- 解釈性を可視化していない。本プロジェクトではRandomForestを用いているが、解釈性の可視化にはSHAPライブラリが最適。xai_for_housing_regressionにてSHAPライブラリを用いた解釈性の可視化を実装した経験があるため、実装の際はそれを参照する。
